# RSS/Atom raw ingestion contract

Implemented flow and future boundaries:

```text
RSS/Atom source -> raw ingestion -> Bronze storage -> future Silver normalization
```

`RssSource` holds a caller-assigned, stable, nonblank source ID, an HTTP(S) feed URI, and enabled state. IDs remain unchanged when feed locations change; uniqueness is the caller's responsibility. URIs require a host and valid port and exclude embedded credentials and fragments. Disabled definitions are valid but retrieval rejects them without a request.

`FeedFetcher` is the retrieval boundary. `HttpFeedFetcher` uses Java 21 `HttpClient` for synchronous GETs. Callers supply a reusable client (including connect timeout, redirect and proxy policy), a positive request timeout, and a clock. Callers own client shutdown. The batch CLI owns the client lifecycle; no service container or configuration framework is used.

`RawFeed` preserves response body bytes without XML parsing, text decoding, article conversion, or content-type filtering. HTTP transfer framing is removed by the HTTP client; these are payload bytes, not a wire capture. Defensive copies protect the payload. Metadata includes a fresh UUID per completed retrieval, stable source ID, UTC instant after body receipt, HTTP status, optional Content-Type, and optional declared Content-Length. Missing length remains absent, including chunked responses; `body().length` is the actual received size.

All 2xx responses within the payload limit succeed, including empty bodies. `FeedFetchException` distinguishes HTTP (all other statuses), transport (`IOException`, including timeouts), interruption (interrupt flag restored), disabled-source failures, and `PAYLOAD_TOO_LARGE`. HTTP failures retain the complete raw response and metadata; transport/interruption failures retain their cause and source ID without fabricating an HTTP response. Redirect behavior follows the supplied client; the JDK default does not follow redirects, so a 3xx then becomes an HTTP failure. Invalid definitions fail immediately with `IllegalArgumentException`; null fetch arguments fail with `NullPointerException`.

The [Bronze storage adapter](bronze-storage.md) preserves the original feed payload and associated provenance; callers explicitly choose whether to persist raw HTTP error responses. Article parsing, malformed XML handling, schema validation, normalization, duplicate article handling, and late-event policy belong downstream in Silver. Fetch success indicates HTTP success only; invalid XML is not silently discarded. Repeated retrievals get different ingestion IDs; this layer promises neither deduplication nor exactly-once delivery. Storage idempotency and retry assumptions are defined in the Bronze contract.

## Payload bounds

The three-argument `HttpFeedFetcher(client, requestTimeout, clock)` constructor defaults to `DEFAULT_MAX_PAYLOAD_BYTES`, 5 MiB (`5 * 1024 * 1024` bytes). The overload `HttpFeedFetcher(client, requestTimeout, clock, maxPayloadBytes)` accepts a positive `int`; zero and negative limits are rejected with `IllegalArgumentException`. Choose a limit appropriate to available memory and concurrency.

A per-response bounded `BodySubscriber` checks every delivered buffer before copying the batch into its own growable byte array. It accepts exactly the limit and cancels the subscription when actual delivered bytes would exceed it. No allocation is based on Content-Length; absent or overstated lengths do not bypass the counter. Accepted payload bytes remain unchanged. The limit applies after HTTP transfer framing is removed, but before any content decompression. This client does not decompress gzip or other content encodings; downstream decompression needs its own size limit.

The subscriber copies only readable bytes (position through limit), including sliced and read-only buffers, and retains no incoming buffers or lists. Delegating accumulation to the JDK byte-array subscriber was removed because that implementation can retain slices and their much larger backing allocations until completion. Copying immediately also avoids retaining one buffer object per fragment.

Storage starts empty. On demand it grows to at least the required size, using an initial target of 1 KiB and subsequent doubling, always capped at the configured limit. Capacity arithmetic uses widened values and payload counting uses subtraction to avoid overflow. Growth occurs per capacity expansion, not per fragment. On success the array is transferred when already exact-sized or trimmed to the actual length; the accumulator reference is cleared. On failure the accumulator reference is also cleared. A single growable array is simpler here than segment bookkeeping and assembly.

The subscriber requests one batch on subscription and another only after copying the current batch, including empty batches. Flow callbacks are serialized. A terminal-state guard ignores late callbacks, duplicate subscriptions are cancelled, and an early header failure cancels the eventual subscription without requesting data.

On overflow, the body stage fails with a dedicated IOException subtype. The fetcher recognizes it through the HTTP client's exception cause chain and reports `PAYLOAD_TOO_LARGE`, retaining the cause and source ID. There is no partial `RawFeed`. Oversize takes precedence over HTTP status: an oversized 503 is `PAYLOAD_TOO_LARGE`, while a complete 503 within the limit remains `HTTP` with its original body and metadata. Subscription cancellation stops further accumulation; late callbacks cannot overwrite the terminal failure.

HTTP framing still belongs to the JDK. Responses containing both Transfer-Encoding and Content-Length are rejected as `TRANSPORT` with a diagnostic cause, before body accumulation: this ambiguous combination can otherwise hide an oversized chunked body behind a small declared length. With Content-Length alone, bytes beyond the declared response length are not delivered as body bytes by the JDK and cannot be counted here. A prematurely closed response remains `TRANSPORT` unless delivered bytes have already exceeded the limit. Thus `PAYLOAD_TOO_LARGE` describes observed overflow, not an unverified header claim.

## Validation and limits

Run `bash scripts/test-ingestion.sh` with JDK 21 and Maven 3.9+ on PATH. The script invokes Maven, compiles with `--release 21`, and runs all ingestion unit tests, including the original Day 2 assertions through a JUnit wrapper. Build output is under ignored `ingestion/target/`. Day 3 introduces SDK, JSON, and JUnit dependencies; bootstrap requires Maven Central, while tests use loopback servers and no public feeds or cloud services. Tests cover byte preservation, metadata, absent headers, unique IDs, defensive copying, HTTP errors, redirects, transport failure, interruption, disabled sources, and invalid definitions. Additional tests cover positive limit validation, below/exact/above-limit fixed and chunked bodies, EOF-delimited bodies, misleading lengths and conflicting framing via a raw loopback server, oversized HTTP errors, client reuse, cancellation across multiple buffers/batches, and late callbacks. Deterministic ownership regressions mutate upstream backing arrays after copying and inspect retained subscriber fields without relying on garbage collection. Additional checks cover large-array slices, nonzero positions, read-only buffers, multi-buffer batches, geometric capacity growth, demand, and cleanup on terminal signals.

Responses are buffered in memory up to the configured limit. Each accumulator array has capacity at most the configured limit. During growth, old and new arrays temporarily coexist; trimming can likewise allocate a result alongside the accumulator. JDK transport buffers, pending garbage collection, and `RawFeed` defensive copies add memory overhead, so the limit is not a total JVM heap cap. Upstream backing allocations are no longer retained by the subscriber after copying. Concurrency is caller-managed, so aggregate memory can grow with simultaneous requests. Streaming to storage, decompression limits, and a global memory budget remain future work. There are no application retries, persistence guarantees, metrics, or logging of payloads/URIs. The JDK may internally retry some connection failures. CI runs Maven verify using its hosted runner's Java 21 installation; patch versions follow the runner image. The Maven migration and storage dependencies are recorded in accepted ADR 0002.

See the [accepted ADR](../adr/0001-rss-raw-ingestion-contract.md) for tradeoffs.

Day 4 connects this contract to Bronze through the [batch runner and CLI](batch-ingestion.md). The runner skips disabled sources and never persists failed retrieval responses. Production retrieval contracts remain unchanged.
