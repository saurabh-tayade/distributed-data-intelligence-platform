## Recommended architecture

1. **PostgreSQL plus Spring JDBC:** use a local PostgreSQL 17 deployment for operational metadata and short transactional state changes. Use versioned Flyway migrations, not JPA or schema auto-update. Pin a maintained patch/image digest and Boot-compatible driver/migration artifacts during checkpoint B; install nothing in Stage A. PostgreSQL adds a local service, but makes queue admission, idempotency, claims, revision capture and audit atomic without a custom file journal database.
2. **Two roles from the existing Spring Boot codebase:** management API mode and one worker-only mode. The worker has no HTTP listener and does not instantiate analytical controllers/query pools. Existing analytics-only startup remains possible without PostgreSQL. Enabled management startup requires a compatible migrated schema. No Maven/npm/pip build runs inside a submitted job.
3. **Host-launched worker and API; containerized PostgreSQL/SeaweedFS:** retain the Bronze clients' loopback policies, local mounts and pinned Python 3.12/Java 21/PySpark 4.0.2/DuckDB 1.4.5 behavior. An all-container worker would require a separate reviewed networking/storage policy; do not weaken LocalS3 to make Compose convenient. PostgreSQL/SeaweedFS ports remain published only on host loopback.
4. **One active managed execution globally:** fixed Content RSS and Reliability-v2 adapters share one persistent coordinator slot and one host filesystem guard. At most twenty unfinished runs are admitted, including active/recovery work. Use ordered transactional row claims; SKIP LOCKED and multi-consumer machinery offer no benefit for this one-worker design. Do not keep SQL transactions open during I/O, Spark actions or child execution.
5. **Immutable capture, not dynamic workflows:** requests use source revision/artifact IDs and server-approved storage/runtime profiles. Freeze submitted selection bytes separately from subsequently verified execution evidence. Changes to sources, references, raw history or semantic selection require a new run; attempts never silently substitute them. References and registered batches remain governed by their existing contracts.
6. **At-least-once attempts, independently verified effects:** reconcile before retry. A valid completed selected result is reused without writes. Namespace absence can permit a fresh invocation; incomplete/corrupt analytical output blocks it. Database fencing prevents stale metadata updates, not filesystem writes. Lease expiry never authorizes another writer.
7. **Explicit operational controls:** request cancellation of queued/running work with bounded child termination and subsequent artifact verification; retry only after guarded reconciliation of frozen evidence. A successful publication found after a cancel request is reported as success with cancellation TOO_LATE. Unknown writer ownership/outcome requires recovery. Pause/resume and process suspension are deferred. No rollback or exactly-once effect is claimed.
8. **Minimal local Operations surface:** source revisions/enablement, exact run submission, bounded history/attempt detail and control acknowledgments. No activation/latest pointer, product query API expansion, raw/quarantine download or export. E6 owns authentication/product authorization/selection and exports; E7 owns broader product UI/release polish. E4a owns performance experiments and detailed hardware instrumentation.

## Run and attempt state machine

Run states are exactly QUEUED, RUNNING, CANCEL_REQUESTED, SUCCEEDED, FAILED, CANCELLED and RECOVERY_REQUIRED. Controls and their acknowledgments are separate durable records. QUEUED -> RUNNING creates a claimed attempt; queued cancellation prevents dispatch. RUNNING can end in verified success, safe failure, proven cancellation or recovery. CANCEL_REQUESTED does not authorize a following stage. Explicit eligible retry permits FAILED/CANCELLED -> QUEUED with the same frozen evidence. SUCCEEDED is final. A verified earlier checkpoint after interruption leads to a closed failed/cancelled outcome and a separate guarded retry, not a paused state or automatic continuation.

Attempt states are exactly CLAIMED, RUNNING, SUCCEEDED, FAILED, CANCELLED and INTERRUPTED. An interrupted attempt means supervision/outcome is uncertain, not that its process is proven dead. A separate RECONCILE attempt appends verified recovery evidence. The supporting contract specifies exact allowed transitions, the occupied-slot ownership handoff and race outcomes; arbitrary state assignment is forbidden. No pause/resume states, controls or UI are required in E5.

The [Proposed platform specification](../product-specification.md#asynchronous-execution-and-recovery) suggests two active runs globally and a cancellation winner that prevents completion. This proposal narrows concurrency to one and makes the cancellation acknowledgment honest about existing publishers: before launch it can prevent that stage; after launch it cannot promise a DB-atomic completion veto. Changing publishers to consult the DB would compromise the retained standalone boundary. These are explicit owner decisions about Proposed operational requirements, not changes to accepted data contracts.

## Persistence and transactional coordination

PostgreSQL owns source/revision records, runtime bindings, runs, frozen selections, attempts, stage intents/checkpoints, RSS delivery intents, artifact linkage, control requests and audit events. Public IDs are opaque; private relative storage addresses are never client-supplied. Canonical bytes/digests are retained alongside relational keys; JSONB reserialization must not define publication or submission identity. SQL checks, unique/foreign keys, partial active indexes and a singleton coordinator row back application transition rules.

Submission commits the idempotency binding, captured configuration, all input links, QUEUED state and audit event together before HTTP 202. Claim commits worker session, increasing owner epoch, attempt ID and active slot before any child launch. Every owner mutation compares run, attempt, epoch and expected row version. Stage intent commits before side effects; checkpoint/result evidence commits after independent verification. A lost DB acknowledgment is resolved by querying the same idempotency/attempt identity; no second blind insertion or publication follows.

An occupied coordinator is transferred only after confirmed old-writer quiescence and an explicit RECONCILE control. One transaction locks/revalidates the coordinator, run, old attempt and control, closes an active old attempt as INTERRUPTED, marks its unresolved stages UNKNOWN, increments the ownership epoch and binds a new reconciliation attempt to the same occupied global slot. It never clears the slot between owners. All updates are conditional on the exact previous binding/version. The new owner may perform read-only artifact verification only after the transfer commit is confirmed. Definite rollback leaves the old binding intact; lost commit acknowledgment is resolved through the same control/attempt identity, never another blind transfer. Real PostgreSQL tests must prove rollback, ambiguous acknowledgment, active-index replacement and stale-owner rejection. The [transactional handoff protocol](../architecture/durable-execution.md#transactional-recovery-handoff-of-an-occupied-coordinator) is normative for this accepted architecture.

PostgreSQL [row locks](https://www.postgresql.org/docs/17/explicit-locking.html) support these short transactions. A lock or heartbeat cannot terminate a Python/JVM process after a database connection disappears. Session advisory locks are therefore not filesystem fencing and are not the recovery authority. A host guard prevents cooperative duplicate workers; the persistent occupied slot plus explicit post-crash quiescence proof prevents automatic takeover when that guard is released by a crashed parent.

Use one migration mechanism; [Spring Boot's migration guidance](https://docs.spring.io/spring-boot/how-to/data-initialization.html) supports that separation. Migrate explicitly with the worker stopped, validate checksums/schema compatibility on startup, and never auto-create an empty replacement database after loss. Database transactions do not atomically commit external files or S3 objects. Retain default durable PostgreSQL settings; single-volume operation and untested backups do not imply high availability or end-to-end power-loss durability.

## Source revisions and RSS identity recovery

Source configuration changes append immutable revisions. Dispatch checks current enablement under the claim transaction; disable prevents queued dispatch without changing already running snapshots. It does not delete historical input or revoke a running revision. Explicit cancellation controls active work. Retrying uses the captured revision, not the current source definition, while still honoring the dispatch enablement gate.

The worker journals the complete original successful RawFeed in a private bounded spool before any Bronze PUT, retaining its generated UUID, ingestion instant, headers permitted by ADR 0002, source URI, bytes, hash and intended keys. Commit the journal descriptor to PostgreSQL before permitting storage. If the fetch is lost before that checkpoint, a subsequent HTTP response cannot stand in for it; require a new run/retrieval. Receipt recovery reopens exact keys and verifies the original evidence, never discovers the newest object. Only an explicit retry may use S3BronzeStorage with the same journaled RawFeed to finish the matching orphan behavior already accepted by ADR 0002. This does not authorize repairing Silver/Gold/Content/Reliability output.

Retries retain exact registered batch/reference completion evidence and frozen Silver/Gold inputs. A publisher shutdown failure or lost response may leave a valid completed publication; reopen it fully and record a recovered success. Missing dependencies are unavailable, corruption is invalid, and demonstrated changes retain changed classifications; ordinary I/O alone is not proof of mutation. Previously selected analytics remain untouched on every outcome.

Imported completed Silver must qualify as managed evidence: bind the exact namespace/source/ingestion identity, retain original completion bytes/digest, capture the complete accepted/rejected file inventory with sizes/hashes and directory/file identities, and use the existing Silver schema/provenance validation. Recheck that evidence after qualification and before downstream use. A completion marker alone is insufficient. Do not rewrite native Silver markers, schemas or replay behavior; missing, corrupt or changed evidence fails closed.

## Alternatives and tradeoffs

| Alternative | Assessment |
| --- | --- |
| SQLite operational store | Plausible for a single owner and avoids another service. Cross-process API/worker claims, write contention and migration/recovery still need design. PostgreSQL provides explicit transactional coordination and fits the requested demonstrable service lifecycle; SQLite remains appropriate for the independent correctness oracle, not a second operational authority |
| In-memory queue / Spring async only | Loses submissions/history/ownership on restart; insufficient |
| Embedded worker in the HTTP role | Fewer launch commands but couples HTTP lifecycle, shutdown and processing resources. A worker-only role is a small, testable separation |
| Containerized worker now | Conflicts with both loopback-only Bronze factories and local path/process assumptions. Host networking is not a portable Docker Desktop solution. Defer until a separate policy and integration proof exist |
| Lease timeout -> reclaim immediately | Unsafe: stale writer/descendants can still finalize immutable namespaces. Block and reconcile instead |
| DB advisory lock alone | Session loss releases coordination without proving process cessation. No external fencing token is consumed by current publishers |
| Generic jobs/DAGs, shell commands, scheduler or established orchestrator | Disproportionate for two fixed pipelines; broader operational/dependency surface without resolving existing publication contracts |
| Retry by deleting partial output or always changing output roots | Hides uncertainty, violates recovery discipline or changes exact downstream evidence. Keep fixed captured roots and require explicit owner investigation |
| New fetch on RSS retry / checksum-based delivery identity | Changes observation identity/history. Reuse the original journaled RawFeed or require a new run |
| Automatic activate-latest on success | Changes accepted consumer selection and introduces E6 selection/authorization concerns. Execution only records candidates |

The selected approach adds database migrations, a private spool and explicit manual recovery work. It deliberately sacrifices automatic failover and defers pause/resume to preserve simple standalone processors and one-writer assumptions. Full verification adds I/O; no latency, throughput, 100K/1M capacity or multi-worker claim is made.

## Security, failure modes and limits

E5 is a trusted single local operator/host boundary, not authentication. Bind API, frontend and database ports to loopback; reject unapproved Host/Origin and cross-origin mutation requests. Use fixed custom request header plus JSON content type for browser mutation protection, without describing that as E6 authorization. Source endpoints and storage/runtime paths are server-reviewed allowlists. Resolve secrets only from ignored operator configuration into the specific child that needs them. Never expose payloads, event/article identities, credentials, process commands, internal paths, SQL or arbitrary exception strings through Operations.

Resource limits include one execution, twenty unfinished runs, bounded source counts/request bodies/history pages/response sizes, capped attempts/checkpoints and stage time/output budgets. Existing parser, row/file, 512 MiB/no-spill and integrity ceilings stay unchanged. Basic admission/free-space checks and stage durations are E5 safety; detailed benchmark collectors/preflights remain E4a. Stop on exhaustion instead of raising budgets. During DB outage, reject new mutation acknowledgments, stop launching stages, request termination of active children, retain ambiguity and require reconciliation. Existing verified analytical reads need not depend on the management DB.

Disk safety requires bounded stage admission, explicit approved roots, native artifact limits, minimum free-space checks and safe handling of exhaustion. Cooperative checks are not hard disk limits; OS-specific filesystem quotas are not an E5 completion requirement. Preserve incomplete artifacts and block unsafe retries. Use persistent local volumes and documented manual retention/recovery procedures, including restricted RSS journal retention. Comprehensive backup/restore automation is deferred; no untested restore, high-availability or power-loss guarantee is claimed. If an operator later restores data, dispatch remains closed until metadata/dependency bindings and old-writer quiescence are explicitly verified.

## Seven owner-accepted decision groups

The owner approved the following seven groups as amended during Stage A.1 on October 20, 2026. Their wording records the reviewed scope; only the B1 subset is authorized for implementation now.

1. **Store and packaging:** approve PostgreSQL 17, Spring JDBC/Flyway and the new local persistent volume; require exact supported patch/image/dependency pins before implementation validation. No cloud or paid service.
2. **Runtime and ownership:** approve host-launched API/one worker, one global active slot, cooperative host guard and the exact transactional reconciliation handoff after confirmed quiescence. No automatic lease takeover or container-worker support.
3. **Adapter/import scope:** approve Content RSS -> Bronze -> Silver -> Gold -> Content and homogeneous registered Reliability v2 JSONL/Parquet, plus operator-only verified import of existing references/batches/Silver with complete managed evidence qualification. Keep v1 historical artifacts/readers unchanged; no raw uploads or reference-authoring UI.
4. **Controls and recovery:** approve cancellation as a request with verified TOO_LATE/UNKNOWN outcomes, bounded guarded retries of identical frozen selections, explicit reconciliation, blocked incomplete analytical namespaces and new-run-only RSS refetch after lost evidence. Pause/resume is deferred. This resolves the stronger cancellation wording in the Proposed platform plan without changing publishers.
5. **Source/security boundary:** approve revisioned reviewed endpoint/profile IDs, live enablement gate, trusted-loopback-only use and minimum Host/Origin/mutation protection. E6 remains required before shared exposure; no claim that local controls authenticate users.
6. **Limits and retention:** approve the supporting contract's numerical E5 starting limits, cooperative disk admission/exhaustion handling, deadlines/cleanup behavior, persistent volumes and manual retention/recovery procedure, including private RSS journals. Hard filesystem quotas and comprehensive backup automation are deferred, not E5 completion gates; no hard disk or untested restore guarantee is implied. No benchmark-derived capacity is claimed.
7. **Delivery boundary:** approve minimal Operations source/run controls only; keep publication activation, new product-report APIs, authorization/exports, UI polish and E4a experiments out of E5. Confirm the supporting acceptance matrix/checkpoints as Stage B scope.
